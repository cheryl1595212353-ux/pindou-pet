# 拼豆虚拟宠物 Web MVP 设计规格

状态：已完成逐段讨论，待书面审阅  
日期：2026-07-16  
首版形态：产品演示优先的 Web 应用

## 1. 产品定义

用户按照引导上传同一只猫的三张照片。系统识别其脸型、体型、毛色和标志性花纹，生成固定正面／四分之三坐姿的分层 2.5D 拼豆宠物。用户经过轻量校正后，可以在网页中与宠物互动，也可以把中立姿势导出为现实中可照着制作的拼豆图纸。

这里的“建模”是二维／准二维虚拟形象的生成、分层和动作绑定，不包括三维网格重建、骨骼蒙皮或完整三维旋转。

首版不是照片滤镜：最终产物必须是一份具有身体层、关节点、动作参数和实体拼豆数据的可复用角色资产。

## 2. 目标和成功定义

首版必须完成以下闭环：

1. 引导用户提交三张合格照片。
2. 在 120 秒内给出可编辑的角色初稿。
3. 经过轻量校正后保留猫的个体身份特征。
4. 生成一份 58×58、固定真实色板的分层拼豆角色资产。
5. 稳定播放呼吸、眨眼、摇尾、抬爪和点击弹跳五个动作。
6. 将同一角色的中立姿势导出为四块 29×29 底板、颜色数量表、PNG 和 PDF。
7. 对至少 5 只、目标 10 只外观不同的猫走通完整流程。

早期讨论中的“歪头”不属于首版五个必验收动作，进入后续动作扩展清单。

## 3. 范围

### 3.1 首版包含

- 仅支持猫。
- 输入正面、左前 45°、右前 45°三张全身照。
- 固定正面／四分之三坐姿，不做完整转身和行走。
- 自动生成加轻量人工校正。
- 58×58 拼豆主网格，对应四块 29×29 底板。
- 一套冻结的真实拼豆色板：首版采用项目内置的 Perler 色板快照 v1，不提供品牌切换。
- 6–8 个角色图层、五个基础动作、网页互动。
- 中立姿势的 PNG、PDF、颜色编号和豆子数量导出。
- 5–10 只猫的验证集，覆盖纯色、橘猫、狸花、奶牛猫、长毛和短毛。

### 3.2 首版不包含

- 狗、其他宠物或任意动物输入。
- 三维重建、三维网格、骨骼蒙皮和完整视角旋转。
- 行走、转身、复杂表情和复杂骨骼动画。
- AR 放置、小程序、原生 App。
- 投喂、心情值、成长、房间、社交等养成玩法。
- 账号、支付、跨设备同步和公众规模运营。
- 多拼豆品牌自由切换。

原始课题描述中的移动端 CPU 50ms、逐帧风格化 500ms 和 AR 15fps 指标不适用于本 Web MVP；它们只能在未来移动端／AR 阶段重新定义和实测。

## 4. 用户流程

### 4.1 创建与上传

用户提交：

- 正面全身照；
- 左前 45°全身照；
- 右前 45°全身照。

上传页检查：

- 是否恰好包含一只猫；
- 是否为要求的视角；
- 身体和尾巴是否基本完整；
- 是否清晰、不过曝、无严重遮挡；
- 三张图片是否明显属于同一只猫。

系统发现明确问题时，必须指出具体照片和原因并要求重拍。若“是否同一只猫”无法可靠判断，则要求用户确认，不得用低置信度结果静默拒绝。

### 4.2 生成与形象确认

从用户点击“生成”开始计时，时间包含照片上传、排队、处理和最多一次自动重试。系统依次完成：

1. 照片解码、方向纠正和 EXIF 移除；
2. 猫咪抠图和质量复检；
3. 汇总脸型、耳形、眼睛、体型、主毛色和标志花纹，形成身份特征卡；
4. 以三张照片和身份特征卡为约束，生成固定三分之四坐姿的高清透明角色；
5. 向用户展示初稿和身份特征卡。

用户可以接受初稿，或标记“脸不对、体型不对、颜色不对、花纹不对”。不接受时只重新执行必要的生成阶段，不重复上传和质量检查。

### 4.3 高清拆层和校正

角色在高分辨率下先拆层，再进行拼豆化。最低图层集合为：

- 身体；
- 头部；
- 左前爪；
- 右前爪；
- 尾巴；
- 眼睛状态层（睁眼与闭眼变体）。

可增加的数字辅助层包括胸口／颈部／尾根隐藏补丁和地面阴影，但数字专用层不得进入实体图纸。

系统只补全动作实际会露出的局部区域，不试图虚构完整三维身体。人工校正工作台提供：

- 画笔补回和橡皮擦除；
- 拖动颈部、左右肩部和尾根关节点；
- 调整图层前后顺序；
- 单独重做错误部件；
- 实时预览五个动作。

进入拼豆化前必须通过三个检查门：

1. 身份检查：角色仍能辨认成输入的猫。
2. 图层检查：边界、关节点、父子层级和遮挡关系完整。
3. 动作检查：五个动作无明显露洞、部件断裂或错误遮挡。

身体边界和关节点校正的体验目标为约 5 分钟；逐豆精修时间不计入该目标。

### 4.4 拼豆化与逐豆精修

通过高清校正后，所有图层共同转换到同一个 58×58 坐标系和同一色板：

- 采用 CIEDE2000 或等价的感知色差匹配；
- 建议使用 16–32 种颜色，但不得生成色板之外的颜色；
- 默认关闭抖动，避免毛发产生随机噪点或跨图层花纹断裂；
- 图层不得各自独立选择色板或重新量化；
- 关节位置预留少量重叠豆格和隐藏补丁。

逐豆编辑器支持画笔、橡皮、填充、吸管、撤销／重做、缩放和平移，并即时显示实体制作风险。

## 5. 角色资产模型

### 5.1 唯一事实源

每只宠物只有一份版本化的“分层拼豆角色资产”。分层资产是唯一事实源；实体中立矩阵是按需派生的缓存，不可单独编辑。

概念数据结构：

```text
project:
  schemaVersion
  projectId
  status
  currentStep
  gridWidth = 58
  gridHeight = 58
  boardSize = 29
  paletteId = "perler-v1"
  activeAssetVersion

assetVersion:
  revision
  sourceHash
  layers[]
  variants[]
  animations[]

layer:
  id
  parentId | null
  zIndex
  pivot { x, y }
  exportPolicy = physical | digital_only | variant
  sparseCells[] { x, y, colorId }
  neutralTransform = identity

animation:
  name
  durationMs
  tracks[layerId][] { timeMs, dx, dy, rotationDeg, easing }
  exportable = false

neutralMatrix:
  derivedFromAssetHash
  cells[58][58]
```

所有坐标都必须在 58×58 内，同一图层同一格最多一颗豆。透明格和白色豆是不同状态。父子图层关系必须无环；眼睛跟随头部，头、前爪和尾巴跟随身体。

数字动画舞台不是 58×58 的硬裁剪框。舞台在角色网格外保留运动留白，但任何实体导出都只读取 58×58 中立姿势。

### 5.2 中立姿势合成

实体图纸按以下规则派生：

1. 强制停止动画并恢复所有图层的单位变换；
2. 排除 `digital_only` 和未激活的变体层；
3. 按 `zIndex` 合成物理图层；
4. 重叠格只保留最上方可见的一颗豆；
5. 生成 58×58 中立矩阵和源资产哈希；
6. 所有图纸和数量统计只读取该矩阵。

动画帧永远不能作为实体拼豆图纸导出。

## 6. 互动与动画

浏览器逐颗绘制拼豆外观，但每个身体层可缓存为一张离屏位图。运行时移动或旋转整层，不把数千颗豆分别创建成 UI 组件。

五个首版动作：

| 动作 | 实现 | 约束 |
| --- | --- | --- |
| 呼吸 | 身体和头部轻微错峰上下移动 | 不拉伸单颗豆 |
| 眨眼 | 睁眼层短暂替换为闭眼层 | 眼睛变体必须跟随头部 |
| 摇尾 | 尾巴绕尾根往返旋转 | 建议约 ±12°，不得露出明显空洞 |
| 抬爪 | 前爪绕肩部抬起 | 建议约 10–15°，隐藏补丁填补胸口 |
| 点击弹跳 | 全角色作为整体上移并回落 | 只平移，不缩放豆子 |

交互规则：

- 待机时循环呼吸，随机触发眨眼和轻微摇尾；
- 点击不同命中区域可触发抬爪或整体弹跳；
- 新动作可以打断当前非关键动作并安全返回中立状态；
- 动作结束后必须精确恢复中立姿势；
- 动作不得修改角色的拼豆矩阵。

从 `pointerdown` 到第一个视觉反馈帧必须不超过 200ms。正式验收同时报告 P95 和最大值。

## 7. 实体拼豆导出

实体导出包包含：

- 58×58 完整彩色预览；
- 左上、右上、左下、右下四块 29×29 底板；
- 板号、方向和拼接定位标记；
- 每格颜色编号；
- Perler 色号、颜色名称、各色数量和总数量；
- 高清 PNG；
- 适合屏幕查看和打印的 PDF。

导出前自动检查：

- 所有颜色属于 `perler-v1` 色板；
- 所有可见豆在 58×58 范围内；
- 四块底板无遗漏、重复或镜像；
- 总豆数等于各色数量之和；
- PDF、PNG 和预览来自同一个资产哈希；
- 孤立豆、仅对角连接和单豆宽脆弱连接被准确定位并提示；
- 分离阴影和其他数字装饰没有进入实体图纸。

制作风险是警告而不是一律阻止导出；用户必须明确确认风险后继续。

## 8. Web 系统设计

### 8.1 架构

首版采用模块化单体加一个独立后台 Worker：

```text
React Web
  ⇅ HTTP + 2 秒状态轮询
FastAPI 单体 API
  ⇅ 项目状态 / 任务入队
Redis + RQ 单 Worker
  ⇅
AI Provider / 图像处理工具

SQLite + 私有文件目录 = 持久状态与资产
```

技术选择：

- 前端：React、TypeScript、Vite；
- 画布：react-konva，用于图层、拖拽、命中检测、画笔和动画；
- 后端：FastAPI；
- 队列：Redis + RQ，单 Worker；
- 数据库：SQLite WAL；
- 文件：单机私有目录和持久卷；
- PNG：Pillow；
- PDF：ReportLab。

30–120 秒的生成任务不得使用 FastAPI 进程内 `BackgroundTasks` 执行。Redis 只负责排队，SQLite 是项目状态和任务状态的事实源。

### 8.2 页面

首版只有四个页面：

1. 创建页：上传三张照片、查看生成进度、确认角色形象。
2. 编辑工作台：高清图层校正和 58×58 逐豆精修两个页签。
3. 互动房间：待机和五个动作。
4. 实体导出：制作风险、四块底板、颜色统计、PNG 和 PDF。

首版不做账号。匿名项目通过随机签名会话访问，并在当前浏览器保存最近项目入口。

### 8.3 后端模块

- `uploads`：上传、解码、质量检查和临时文件生命周期；
- `jobs`：幂等任务、状态和重试；
- `pipeline`：生成阶段编排与检查点；
- `providers`：第三方生成和分割服务适配器；
- `assets`：角色 JSON、版本、校验和派生中立矩阵；
- `exports`：PNG、PDF 和颜色统计。

生成服务必须通过统一 Provider 接口接入并固定模型版本。前端不得直接持有第三方 API 密钥，也不得依赖某个供应商的原始响应结构。

首版 Provider 合同：

```text
GenerationProvider:
  submit(request) -> providerJobId
  status(providerJobId) -> state
  result(providerJobId) -> normalizedImageResult
  cancel(providerJobId)

SegmentationProvider:
  segment(image, prompts) -> normalizedMasks
```

具体供应商可以替换，但进入产品验证的模型名称、版本号、请求参数和留存政策必须冻结并记录。

### 8.4 状态和失败恢复

项目主状态：

```text
UPLOADED -> PROCESSING -> LAYER_REVIEW -> BEAD_REVIEW -> READY
```

另有 `FAILED`、`CANCELLED`、`EXPIRED`，具体处理阶段记录在 `currentStep`，不建立更细的全局状态机。

可靠性规则：

- 阶段任务键由 `projectId + stage + inputHash + revision` 组成，并设置唯一约束；
- 重复点击不会创建第二个收费任务；
- 保存第三方 `providerJobId`，Worker 重启后继续查询而不是重复提交；
- 网络超时和服务端 5xx 最多自动重试一次；
- 照片不合格、内容拒绝或用户不满意不自动循环生成；
- 每个昂贵阶段成功后保存检查点；
- 文件先写入临时路径，再原子替换正式文件；
- 编辑保存携带 `revision`，旧版本保存返回冲突而不是覆盖；
- 用户批准后生成不可变资产版本；后续编辑必须创建新版本。

## 9. 隐私和数据生命周期

- 上传前明确说明照片会发送给第三方处理，并取得用户同意；取消同意时不得上传图片。
- 接收后立即解码、纠正方向、移除 EXIF，存储名使用随机 ID，不保留原文件名。
- 原始照片和未确认的生成中间物在任务完成或取消后 24 小时内从本系统删除。
- 长期保留用户确认的高清分层角色、拼豆资产、动作参数和导出文件。
- 用户可以主动“删除宠物”，删除角色资产、导出文件和数据库引用。
- 日志不得记录图片、Base64、永久文件 URL、原始文件名、API 密钥或完整第三方响应。
- 只有第三方供应商提供零留存或可验证删除机制时，产品才能宣称“照片已从所有处理方删除”；否则文案必须限定为“已从本系统存储删除”。

## 10. 开源复用边界

可借鉴 [Fusible Beads Studio](https://github.com/yourlin/Fusible-Beads-Studio) 的 MIT 许可实现，尤其是：

- 拼豆色板数据结构；
- CIEDE2000 颜色匹配；
- 逐豆编辑交互；
- 四底板切分、PNG／PDF 和颜色数量思路。

其 Vue 页面不直接复制到 React 应用；优先复用或移植框架无关的逻辑。复制任何代码前必须复核具体文件许可，并在项目中保留许可证和归属说明。

[Image-to-Pixel](https://github.com/Tezumie/Image-to-Pixel) 的 MIT JavaScript 库可作为通用像素化对照实现，但首版拼豆主路径以真实色板匹配为准。

这两个项目都不解决猫咪身份融合、身体部件拆层、遮挡补全、关节点和动画绑定，这些仍属于本产品自己的生成与编辑流程。

## 11. 验收与测试

### 11.1 验收样本

- 开发阶段至少 5 只猫；正式验收目标 10 只。
- 覆盖纯色、橘猫、狸花、奶牛猫、长毛和短毛。
- 每只猫有三张规范输入照片。
- 另建错误输入集：缺图、重复视角、狗、多猫、模糊、裁脚、背面、严重遮挡和明显不是同一只猫。

### 11.2 量化标准

| 维度 | 通过标准 |
| --- | --- |
| 输入 | 明确错误被定位到具体照片；合格组可进入生成 |
| 初稿时间 | 从点击生成到可编辑初稿，每个正式验收样本不超过 120 秒，包含上传、排队和一次自动重试 |
| 个体相似度 | 人工校正后脸型、体型、主毛色和标志花纹均保留；3 人盲评平均 ≥4/5，单只猫 ≥3.5/5 |
| 自动拆层 | 6–8 个有效层，必需层、父子关系、关节点和层级完整 |
| 人工校正 | 受过简短引导的测试者约 5 分钟内完成身体校正；逐豆精修另计 |
| 拼豆资产 | 无越界、非法色号、同层重复格或父子环；保存后逐格一致 |
| 动作 | 五个动作无拉伸、明显露洞、断裂、错误遮挡或裁切；结束精确回中立 |
| 互动延迟 | 冻结设备和浏览器后，每只猫每个动作触发 30 次，最大值 ≤200ms，并报告 P95 |
| 实体导出 | 四块 29×29 重组后与 58×58 中立矩阵逐格完全一致 |
| 数量 | 各色数量之和等于中立矩阵非空格总数 |
| 恢复 | 刷新、断网、供应商超时、重复提交和 Worker 重启不丢失已确认结果，也不创建重复资产 |
| 删除 | 测试 TTL 到期后原图和临时物从本系统各存储位置消失；主动删除后资产不可访问 |

正式验收前必须冻结测试手机、桌面设备、浏览器版本和网络条件，以保证时间数据可复现。

### 11.3 测试层次

- 单元测试：色差匹配、矩阵合成、父子变换、数量统计、底板切分和角色 JSON 校验。
- Provider 契约测试：固定假服务覆盖成功、超时、限流、内容拒绝和异常结果。
- API／队列集成测试：幂等、重试、检查点、Worker 重启和 TTL 删除。
- 端到端测试：上传、生成、校正、逐豆编辑、互动和导出完整主路径。
- 视觉回归：五个动作关键帧、角色中立姿势和四块底板截图。
- 文件验证：实际打开 PNG 和 PDF，检查方向、编号、字体、色号和打印预览。

## 12. 风险与停线条件

最大风险不是网页架构，而是三张照片能否稳定保留同一只猫的身份并得到可拆层角色。

正式搭建完整互动与导出体验前，应先用 3 只外观差异明显的猫完成生成质量验证。若每只猫在不超过约 5 分钟的身体校正后，仍不能同时通过身份、图层和动作检查，则暂停扩展页面功能，调整生成供应商、标准姿势策略或拆层方式。

其他风险：

- 第三方模型更新造成输出漂移：固定模型版本和请求参数，并保留契约样本。
- 生成费用失控：阶段幂等、最多一次自动重试、记录供应商任务 ID。
- 拼豆颜色在屏幕和实物中存在差异：冻结色板版本，在产品中说明显示器和批次色差。
- 图案物理结构脆弱：检测孤立豆、对角连接和单豆宽连接，但由用户最终确认。
- 单机存储不适合公众规模：真实并发超过约 5 个生成任务或需要跨设备后，再迁移 PostgreSQL 和对象存储。

## 13. 后续阶段

首版验证通过后，按价值和依赖顺序考虑：

1. 新增歪头、转头和更多点击反馈；
2. 小程序／App 端角色查看与互动；
3. 投喂、心情和简单养成；
4. 狗和其他宠物模板；
5. 多色板和采购清单；
6. AR 平面放置；
7. 多方向角色、行走与转身。

任何后续阶段都继续复用本规格中的版本化拼豆角色资产，而不是重新定义另一套角色格式。
