# 拼豆虚拟宠物 Web MVP 设计规格

状态：已完成逐段讨论，待书面审阅  
日期：2026-07-16  
首版形态：产品演示优先的 Web 应用

## 1. 产品定义

用户按照引导上传同一只猫的三张照片。系统识别其脸型、体型、毛色和标志性花纹，生成脸朝向用户、身体向画面右侧偏转约 20°、尾巴位于画面右侧的分层 2.5D 拼豆宠物。用户经过轻量校正后，可以在网页中与宠物互动，也可以把中立姿势导出为现实中可照着制作的拼豆图纸。

这里的“建模”是二维／准二维虚拟形象的生成、分层和动作绑定，不包括三维网格重建、骨骼蒙皮或完整三维旋转。

首版不是照片滤镜：最终产物必须是一份具有身体层、关节点、动作参数和实体拼豆数据的可复用角色资产。

## 2. 目标和成功定义

首版必须完成以下闭环：

1. 引导用户提交三张合格照片。
2. 在正常验收条件下，点击“生成”后 120 秒内给出可供用户确认的高清角色初稿。
3. 经过轻量校正后保留猫的个体身份特征。
4. 生成一份 58×58、固定真实色板的分层拼豆角色资产。
5. 稳定播放呼吸、眨眼、摇尾、抬爪和点击弹跳五个动作。
6. 将同一角色的中立姿势导出为四块 29×29 底板、颜色数量表、PNG 和 PDF。
7. 正式通过门槛为 5 只外观不同的猫全部走通完整流程；扩展验证报告使用 10 只。

早期讨论中的“歪头”不属于首版五个必验收动作，进入后续动作扩展清单。

## 3. 范围

### 3.1 首版包含

- 仅支持猫。
- 输入正面、左前 45°、右前 45°三张全身照。
- 固定模板为：脸朝向用户，身体向画面右侧偏转约 20°，尾巴位于画面右侧的三分之四坐姿；不做完整转身和行走。
- 自动生成加轻量人工校正。
- 58×58 拼豆主网格，对应四块 29×29 底板。
- 一套冻结的真实拼豆品牌／系列色板，不提供用户品牌切换。品牌是部署配置而不是用户选项；正式验收前必须冻结品牌、系列、色板来源、版本和文件校验和。
- 6–8 个角色图层、五个基础动作、网页互动。
- 中立姿势的 PNG、PDF、颜色编号和豆子数量导出。
- 正式验收集为 5 只猫，覆盖纯色、橘猫、狸花、奶牛猫以及长／短毛差异；扩展报告再增加至 10 只。

### 3.2 首版不包含

- 狗、其他宠物或任意动物输入。
- 三维重建、三维网格、骨骼蒙皮和完整视角旋转。
- 行走、转身、复杂表情和复杂骨骼动画。
- AR 放置、小程序、原生 App。
- 投喂、心情值、成长、房间、社交等养成玩法。
- 账号、支付、跨设备同步和公众规模运营。
- 多拼豆品牌自由切换。

原始课题描述中的移动端 CPU 50ms、逐帧风格化 500ms 和 AR 15fps 指标不适用于本 Web MVP；它们只能在未来移动端／AR 阶段重新定义和实测。

## 4. 用户流程

### 4.1 创建与上传

用户提交：

- 正面全身照；
- 从猫的左前方拍摄的全身照；
- 从猫的右前方拍摄的全身照。

两个侧前方视角允许在 30°–60°内偏差。三张照片应尽量保持相同的站／坐姿态、相近距离和相近光照；上传卡片使用示意轮廓明确方向，不只依赖“左／右”文字。

上传页检查：

- 是否恰好包含一只猫；
- 是否为要求的视角；
- 身体和尾巴是否基本完整；
- 是否清晰、不过曝、无严重遮挡；
- 三张图片是否明显属于同一只猫。

系统发现明确问题时，必须指出具体照片和原因并要求重拍。若“是否同一只猫”无法可靠判断，则要求用户确认，不得用低置信度结果静默拒绝。

### 4.2 生成与形象确认

用户先完成三张照片上传和入口质量检查，再点击“生成”。正常路径的计时从服务端接受生成请求开始，到高清角色初稿可供用户确认时结束；不包含用户查看和反馈时间，也不包含之后的高清拆层。系统依次完成：

1. 照片解码、方向纠正和 EXIF 移除；
2. 猫咪抠图和质量复检；
3. 汇总脸型、耳形、眼睛、体型、主毛色和标志花纹，形成身份特征卡；
4. 以三张照片和身份特征卡为约束，生成脸朝向用户、身体向画面右侧偏转约 20°、尾巴位于画面右侧的高清透明角色；
5. 向用户展示初稿和身份特征卡。

用户可以接受初稿，或标记“脸不对、体型不对、颜色不对、花纹不对”。不接受时只重新执行必要的生成阶段，不重复上传和质量检查。用户反馈、生成尝试编号和随机种子都进入新一轮输入哈希，因此合法重生成不会被幂等约束误判为重复提交。

正式验收中，每只猫最多允许初稿之后再完整重生成 1 次、局部部件重生成 2 次；这三类服务端生成等待累计不得超过 300 秒。超过次数或累计时间即判该猫的生成流程未通过，不能靠无限重试后再计为成功。

### 4.3 高清拆层和校正

角色在高分辨率下先拆层，再进行拼豆化。验收按“逻辑图层组”计数：高清层及其对应拼豆层只计一个组，睁眼／闭眼变体共同计一个眼睛组，隐藏补丁、阴影和其他 `physicalExport=false` 辅助层不计入 6–8 个组。六个必需逻辑组为：

- 身体；
- 头部；
- 左前爪；
- 右前爪；
- 尾巴；
- 眼睛状态层（睁眼与闭眼变体）。

可选第 7–8 个逻辑组只用于确有独立运动或遮挡需求的耳朵、口鼻等语义部件。

可增加的数字辅助层包括胸口／颈部／尾根隐藏补丁和地面阴影，但数字专用层不得进入实体图纸。系统同时保存每个已确认高清层的透明 PNG、掩码、补全区域和内容哈希，供后续重新拼豆化和局部修正使用。

系统只补全动作实际会露出的局部区域，不试图虚构完整三维身体。人工校正工作台提供：

- 画笔补回和橡皮擦除；
- 拖动颈部、左右肩部和尾根关节点；
- 调整图层前后顺序；
- 单独重做错误部件；
- 实时预览五个动作。

进入拼豆化前必须通过三个检查门：

1. 身份检查：角色仍能辨认成输入的猫。
2. 图层检查：边界、关节点、父子层级和遮挡关系完整。
3. 动作检查：五个动作无明显露洞、部件断裂或错误遮挡。

校正计时从有效高清拆层草稿打开开始，到身份、图层和动作三道检查门通过为止；不包含等待单部件重新生成的网络时间。测试者先接受一次 5 分钟操作演示。正式验收要求 5 只猫的校正用时中位数不超过 5 分钟，任一只不超过 10 分钟；逐豆精修另计。

### 4.4 拼豆化与逐豆精修

通过高清校正后，所有图层共同转换到同一个 58×58 坐标系和同一色板：

- 将 8 位 sRGB 按 D65 白点转换到 CIELAB，并采用固定版本的 CIEDE2000 感知色差匹配；
- 自动为整只角色选择最多 32 种颜色的全局子色板，逐豆编辑也只允许使用该子色板；
- 默认关闭抖动，避免毛发产生随机噪点或跨图层花纹断裂；
- 图层不得各自独立选择色板或重新量化；
- 关节位置预留少量重叠豆格和隐藏补丁。

逐豆编辑器支持画笔、橡皮、填充、吸管、撤销／重做、缩放和平移，并即时显示实体制作风险。

## 5. 角色资产模型

### 5.1 唯一事实源

每只宠物拥有一个可变草稿和一系列不可变的已批准资产包。草稿通过 `revision` 乐观锁编辑；用户批准时生成不可变快照。已批准资产包同时包含高清分层源和拼豆分层数据，两者通过内容哈希关联：高清层是重新拼豆化的输入，经过人工逐豆修正后的拼豆层是互动和实体导出的权威数据。实体中立矩阵只是由已批准拼豆层派生的缓存，不可单独编辑。

概念数据结构：

```text
project:
  schemaVersion
  projectId
  status
  currentStep
  gridWidth = 58
  gridHeight = 58
  boardSize = 29
  activeAssetVersion

draftAsset:
  revision
  sourceHash
  paletteManifest
  quantizerManifest
  sourceLayers[]
  beadLayers[]
  variantGroups[]
  animations[]

approvedAssetVersion:
  immutableVersionId
  approvedAt
  canonicalAssetHash
  paletteManifest { brand, series, version, sourceChecksum, pegPitchMm, colors[] }
  quantizerManifest { version, colorSpace, whitePoint, distanceFormula, tieBreakRule, maxColors }
  sourceLayers[]
  beadLayers[]
  variantGroups[]
  animations[]

sourceLayer:
  id
  parentId | null
  zIndex
  imageContentHash
  maskContentHash
  completionMaskHash | null

beadLayer:
  id
  parentId | null
  zIndex
  pivotGlobal { x, y }
  physicalExport: boolean
  variantGroupId | null
  variantId | null
  sparseCells[] { x, y, colorId }
  neutralTransform = identity

variantGroup:
  id
  neutralVariantId
  layerIds[]

animation:
  name
  durationMs
  tracks[layerId][] { timeMs, dx, dy, rotationDeg, easing }
  exportable = false

neutralMatrix:
  derivedFromCanonicalAssetHash
  cells[58][58]
```

所有豆格和枢轴均使用中立姿势下的全局网格坐标，原点在 58×58 左上角，`x` 向右、`y` 向下，单位为一格。旋转角度以顺时针为正。父变换先于子变换应用；动画数据不允许缩放。所有豆格必须在 58×58 内，同一图层同一格最多一颗豆，所有同时可见的图层必须具有唯一 `zIndex`。透明格和白色豆是不同状态。父子图层关系必须无环；眼睛跟随头部，头、前爪和尾巴跟随身体。

中立变体由 `variantGroup.neutralVariantId` 明确指定；眼睛组的中立变体是睁眼层。规范化资产 JSON 使用 UTF-8、字典键排序和稳定数组顺序。`canonicalAssetHash` 覆盖高清／拼豆层、动作、完整色板清单和量化清单，但不包含派生预览文件。色差并列时按 `colorId` 升序选择。每个导出包使用 `canonicalAssetHash + rendererVersion` 作为缓存键并记录二者，渲染器升级不会静默改写旧导出。

数字动画舞台不是 58×58 的硬裁剪框。舞台在角色网格外保留运动留白，但任何实体导出都只读取 58×58 中立姿势。

### 5.2 中立姿势合成

实体图纸按以下规则派生：

1. 强制停止动画并恢复所有图层的单位变换；
2. 排除 `physicalExport=false` 的图层，并只激活每个变体组的 `neutralVariantId`；
3. 按 `zIndex` 合成物理图层；
4. 重叠格只保留最上方可见的一颗豆；
5. 生成 58×58 中立矩阵和已批准资产哈希；
6. 所有图纸和数量统计只读取该矩阵。

动画帧永远不能作为实体拼豆图纸导出。

## 6. 互动与动画

浏览器逐颗绘制拼豆外观，但每个身体层可缓存为一张离屏位图。运行时移动或旋转整层，不把数千颗豆分别创建成 UI 组件。

五个首版动作：

| 动作 | 实现 | 约束 |
| --- | --- | --- |
| 呼吸 | 身体和头部轻微错峰上下移动 | 不拉伸单颗豆 |
| 眨眼 | 睁眼层短暂替换为闭眼层 | 眼睛变体必须跟随头部 |
| 摇尾 | 尾巴绕尾根往返旋转 | 建议约 ±12°，不得露出明显空洞 |
| 抬爪 | 画面左侧前爪绕肩部抬起 | 旋转约 10–15°，隐藏补丁填补胸口 |
| 点击弹跳 | 全角色作为整体上移并回落 | 只平移，不缩放豆子 |

交互规则：

- 待机时循环呼吸，随机触发眨眼和轻微摇尾；
- 点击不同命中区域可触发抬爪或整体弹跳；
- 同一时刻只运行一个非中立动作；用户动作优先于待机动作，新动作不会排队；
- 用户触发时先在 100ms 内取消当前待机动作并恢复中立，再执行抬爪或弹跳；
- 动作结束后必须精确恢复中立姿势；
- 动作不得修改角色的拼豆矩阵。

从 `pointerdown` 的 `event.timeStamp` 到首次提交包含该动作视觉变化的 `requestAnimationFrame` 必须不超过 200ms。前台标签页预热 3 次后进行正式测试，同时报告 P95 和最大值。互动房间在冻结的桌面和移动测试设备上，五个动作播放期间的 P95 帧时间不得超过 33.3ms，即至少维持约 30fps。

## 7. 实体拼豆导出

实体导出包包含：

- 58×58 完整彩色预览；
- 左上、右上、左下、右下四块 29×29 底板；
- 板号、方向和拼接定位标记；
- 每格颜色编号；
- 验收时所冻结品牌／系列的色号、颜色名称、各色数量和总数量；
- 高清 PNG；
- 适合屏幕查看和打印的 PDF。

导出前自动检查：

- 所有颜色属于该项目记录的冻结色板版本；
- 所有可见豆在 58×58 范围内；
- 四块底板无遗漏、重复或镜像；
- 总豆数等于各色数量之和；
- PDF、PNG 和预览来自同一个资产哈希；
- 孤立豆、仅对角连接和单豆宽脆弱连接被准确定位并提示；
- 分离阴影和其他数字装饰没有进入实体图纸。

物理连通性按四邻域计算，对角接触不视为熔接。PDF 使用 A4，每块 29×29 底板各占一页，以所选拼豆系列配套底板的实际孔距按 1:1 比例绘制，并附 50mm 校准线；另提供完整预览页和材料清单页。

制作风险是警告而不是一律阻止导出；用户必须明确确认风险后继续。

## 8. Web 系统设计

### 8.1 架构

首版采用模块化单体加一个带 RQ 调度功能的独立后台 Worker；数据库中的单一生成租约保证本地处理和外部 Provider 任务都严格串行：

```text
React Web（桌面编辑，桌面／移动互动）
  ⇅ HTTP + 2 秒状态轮询
FastAPI 单体 API
  ⇅ 项目状态 / 任务入队
Redis + RQ 单 Worker（启用 scheduler）
  ⇅
AI Provider / 图像处理工具

SQLite + 私有文件目录 = 持久状态与资产
```

技术选择：

- 前端：React、TypeScript、Vite；
- 画布：react-konva，用于图层、拖拽、命中检测、画笔和动画；
- 后端：FastAPI；
- 队列：Redis + RQ，单 Worker并启用调度器；
- 数据库：SQLite WAL；
- 文件：单机私有目录和持久卷；
- PNG：Pillow；
- PDF：ReportLab。

30–120 秒的生成任务不得使用 FastAPI 进程内 `BackgroundTasks` 执行。Redis 只负责排队，SQLite 是项目状态和任务状态的事实源。

第三方异步任务提交后，Worker 不持续占用进程等待。它保存供应商任务 ID，再通过延迟任务短轮询并重新入队，但在供应商任务结束前不释放 SQLite 中的单一生成租约，因此不会提交第二个项目的外部生成。Worker／API 启动时扫描 SQLite 中未结束的阶段并重建丢失的 RQ 任务。

隐私到期清理由独立于 RQ Worker 的轻量 janitor／系统定时任务每小时执行。API 启动前先执行一次追赶清理；任何读取请求也先检查到期时间，已到期内容立即返回不可用并触发清理。

### 8.2 页面

首版只有四个页面：

1. 创建页：上传三张照片、查看生成进度、确认角色形象。
2. 编辑工作台：高清图层校正和 58×58 逐豆精修两个页签。
3. 互动房间：待机和五个动作。
4. 实体导出：制作风险、四块底板、颜色统计、PNG 和 PDF。

首版不做账号。匿名项目通过随机签名会话访问，并在当前浏览器保存最近项目入口。

高清图层和逐豆编辑器只承诺桌面浏览器，验收视口不小于 1280×800。创建页、进度、互动房间和导出预览支持桌面与移动浏览器；移动端首版不承担精细画笔编辑。

### 8.3 后端模块

- `uploads`：上传、解码、质量检查和临时文件生命周期；
- `jobs`：幂等任务、状态和重试；
- `pipeline`：生成阶段编排与检查点；
- `providers`：第三方生成和分割服务适配器；
- `assets`：角色 JSON、版本、校验和派生中立矩阵；
- `exports`：PNG、PDF 和颜色统计。

生成服务必须通过统一 Provider 接口接入并固定模型版本。前端不得直接持有第三方 API 密钥，也不得依赖某个供应商的原始响应结构。

首版 Provider 合同：

```text
GenerationProvider:
  submit(request, idempotencyKey) -> providerJobId
  status(providerJobId) -> state
  result(providerJobId) -> normalizedImageResult
  cancel(providerJobId)

GenerationRequest:
  referenceImages[3]
  identityTraits
  targetPose
  editMask | null
  editInstruction | null
  attempt
  seed

SegmentationProvider:
  segment(image, partLabels, pointOrBoxPrompts) -> normalizedPartMasks
```

首版生成 Provider 必须支持确定性幂等键，或支持使用客户端提交键查询既有任务；不满足该条件的供应商不得进入 MVP。合同必须覆盖三张参考图、身份约束、固定姿势、遮罩局部重绘和可固定随机种子的能力。具体供应商可以替换，但进入产品验证的模型名称、版本号、请求参数和留存政策必须冻结并记录。

首版分割在 Worker 内使用固定版本的本地确定性模型，并按输入哈希保存检查点，不产生远程计费提交。若未来改为远程分割服务，必须先为它补齐与 `GenerationProvider` 相同的幂等键、任务查询和对账合同。

在完整页面实施前先完成三猫可行性试验，交付标准姿势图、部件掩码、局部补全结果和固定输入的重复生成记录。试验通过才选择正式 Provider；这是一道实施入口门，而不是运行时未决选项。

### 8.4 状态和失败恢复

项目主状态：

```text
UPLOADED -> PROCESSING -> LAYER_REVIEW -> BEAD_REVIEW -> READY
```

另有 `FAILED`、`CANCELLED`、`EXPIRED`，具体处理阶段记录在 `currentStep`，不建立更细的全局状态机。

可靠性规则：

- 阶段任务键由 `projectId + stage + inputHash + revision` 组成，并设置唯一约束；
- 重复点击不会创建第二个收费任务；
- 提交前先在 SQLite 持久化幂等键和 `SUBMITTING` 状态；供应商按相同幂等键返回同一任务；成功后保存 `providerJobId`，Worker 重启后继续查询而不是重复提交；
- 若供应商返回结果未知且无法按幂等键查询，阶段进入 `SUBMIT_UNKNOWN`，禁止自动重提，必须先对账；
- 网络超时和服务端 5xx 最多自动重试一次；
- 照片不合格、内容拒绝或用户不满意不自动循环生成；
- 每个昂贵阶段成功后保存检查点；
- 文件先写入临时路径，再原子替换正式文件；
- 编辑保存携带 `revision`，旧版本保存返回冲突而不是覆盖；
- 用户批准后生成不可变资产版本；后续编辑必须创建新版本。

用户删除或 TTL 到期时，API 先在同一事务中写入墓碑、撤销访问并创建删除清单，再尽力取消已知供应商任务。Worker 在调用供应商前、收到结果后以及每次写文件／数据库前都必须重查墓碑；晚到结果直接丢弃，不能重新创建资产。墓碑和删除清单保留到所有目标均确认清除后，才删除剩余项目记录。

## 9. 隐私和数据生命周期

- 上传前明确说明照片会发送给第三方处理，并取得用户同意；取消同意时不得上传图片。
- 接收后立即解码、纠正方向、移除 EXIF，存储名使用随机 ID，不保留原文件名。
- 原始照片创建时即写入 `expiresAt = createdAt + 24h`，不因项目成功、失败、取消、关闭浏览器或停留在审核页而改变。
- 未确认的生成中间物在最后一次项目活动 24 小时后删除，且从创建起最长保留 7 天。
- 已确认的资产包默认保留至最后访问后 180 天；每次有效访问重新计算期限，页面明确显示到期时间。
- PNG 和 PDF 按需重新生成，导出文件最长保留 24 小时，不作为长期事实源。
- 用户可以主动“删除宠物”，删除角色资产、导出文件和数据库引用。
- 在服务正常运行时，独立清理器每小时运行一次，因此本系统的最大删除延迟为到期时间后 1 小时；服务中断时，API 重启前执行追赶清理。到期项目进入 `EXPIRED`，读取路径即使尚未物理清理也不得返回内容。
- Redis 任务载荷只保存 ID，不保存图片；首版不做备份，缩略图、缓存和临时文件均受同一到期清单管理。
- 日志不得记录图片、Base64、永久文件 URL、原始文件名、API 密钥或完整第三方响应。
- 只有第三方供应商提供零留存或可验证删除机制时，产品才能宣称“照片已从所有处理方删除”；否则文案必须限定为“已从本系统存储删除”。

## 10. 开源复用边界

可借鉴 [Fusible Beads Studio](https://github.com/yourlin/Fusible-Beads-Studio) 的 MIT 许可实现，尤其是：

- 拼豆色板数据结构；
- CIEDE2000 颜色匹配；
- 逐豆编辑交互；
- 四底板切分、PNG／PDF 和颜色数量思路。

其 Vue 页面不直接复制到 React 应用；优先复用或移植框架无关的逻辑。复制任何代码前必须复核具体文件许可，并在项目中保留许可证和归属说明。

[Image-to-Pixel](https://github.com/Tezumie/Image-to-Pixel) 的 MIT JavaScript 库可作为通用像素化对照实现，但首版拼豆主路径以真实色板匹配为准。

这两个项目都不解决猫咪身份融合、身体部件拆层、遮挡补全、关节点和动画绑定，这些仍属于本产品自己的生成与编辑流程。

## 11. 验收与测试

### 11.1 验收样本

- 正式通过使用 5 只猫；扩展验证报告使用 10 只。
- 覆盖纯色、橘猫、狸花、奶牛猫、长毛和短毛。
- 每只猫有三张规范输入照片。
- 另建错误输入集：缺图、重复视角、狗、多猫、模糊、裁脚、背面、严重遮挡和明显不是同一只猫。

### 11.2 量化标准

| 维度 | 通过标准 |
| --- | --- |
| 输入 | 明确错误被定位到具体照片；合格组可进入生成 |
| 初稿时间 | 三图已上传且入口检查通过、队列为空时，从服务端接受“生成”请求到高清形象确认初稿可见；5 个正常路径样本均 ≤120 秒，不注入故障，也不包含用户查看时间和后续拆层 |
| 个体相似度 | 评分对象是最终批准的 58×58 中立拼豆角色，以 8 倍最近邻方式显示；3 名评审查看三张参考图和匿名角色，平均 ≥4/5，单只猫 ≥3.5/5；高清初稿评分只作诊断，不替代该门槛 |
| 自动拆层 | 校正前即存在 6–8 个非空逻辑图层组；六个必需组的高清图／掩码、对应拼豆层、父子关系、唯一层级和关节点字段完整；变体与辅助层不重复计数 |
| 人工校正 | 接受 5 分钟操作演示后，5 只猫的身体校正中位数 ≤5 分钟，任一只 ≤10 分钟；不计单部件重生成等待和逐豆精修 |
| 拼豆资产 | 无越界、非法色号、同层重复格或父子环；保存后逐格一致 |
| 动作 | 五个动作无拉伸、部件脱离、错误遮挡或裁切；关键帧的关节透明缺口不得大于一颗豆直径；结束精确回中立 |
| 互动性能 | 冻结设备和浏览器后，每只猫每个动作触发 30 次；首帧最大值 ≤200ms，并报告 P95；动作期间 P95 帧时间 ≤33.3ms |
| 实体导出 | 四块 29×29 重组后与 58×58 中立矩阵逐格完全一致 |
| 数量 | 各色数量之和等于中立矩阵非空格总数 |
| 恢复 | 刷新、断网、供应商超时、重复提交和 Worker 重启不丢失已确认结果；供应商 `submit` 对同一幂等键只产生一个任务；故障任务在 10 分钟内完成或进入可解释的失败／对账状态 |
| 删除 | 使用假时钟验证原图、未确认中间物、确认资产和导出的各自 TTL；到期后 1 小时内从文件、缓存、缩略图、队列载荷和数据库引用中消失 |
| 重生成上限 | 每只猫完整重生成最多 1 次、局部重生成最多 2 次；服务端生成等待累计 ≤300 秒 |

正式验收前必须冻结测试手机、桌面设备、浏览器版本和网络条件，以保证时间数据可复现。

相似度采用 1–5 分锚定量表：1 分表示明显不是同一只猫或多项关键特征错误；3 分表示主毛色和体型大致正确但脸型／标志花纹仍有明显偏差；5 分表示可立即辨认为同一只猫且四类身份特征均保留。评审不知道生成供应商和通过阈值。

### 11.3 测试层次

- 单元测试：固定色板与量化版本下的色差匹配、规范化哈希、矩阵合成、父子变换、数量统计、四邻域风险、底板切分和角色 JSON 校验。
- Provider 契约测试：固定假服务覆盖成功、超时、限流、内容拒绝和异常结果。
- API／队列集成测试：在提交前、供应商接受后、保存任务 ID 前后和写文件前后分别注入崩溃，验证幂等、对账、检查点、Worker 重启和 TTL 删除。
- 端到端测试：上传、生成、校正、逐豆编辑、互动和导出完整主路径。
- 视觉回归：五个动作关键帧、角色中立姿势和四块底板截图。
- 文件验证：实际打开 PNG 和 PDF，检查方向、编号、字体、色号和打印预览。

## 12. 风险与停线条件

最大风险不是网页架构，而是三张照片能否稳定保留同一只猫的身份并得到可拆层角色。

正式搭建完整互动与导出体验前，应先用 3 只外观差异明显的猫完成生成质量验证。若三只猫不能全部满足本规格的身份评分，并在已定义的校正时限内通过图层和动作检查，则暂停扩展页面功能，调整生成供应商、标准姿势策略或拆层方式。

其他风险：

- 第三方模型更新造成输出漂移：固定模型版本和请求参数，并保留契约样本。
- 生成费用失控：阶段幂等、最多一次自动重试、记录供应商任务 ID。
- 拼豆颜色在屏幕和实物中存在差异：冻结色板版本，在产品中说明显示器和批次色差。
- 图案物理结构脆弱：检测孤立豆、对角连接和单豆宽连接，但由用户最终确认。
- 单 Worker 明确只服务串行产品演示；一旦需要同时处理两个以上生成任务、跨设备访问或公开运营，先重新评审并发、数据库和对象存储方案，不沿用本规格的单机容量假设。

## 13. 后续阶段

首版验证通过后，按价值和依赖顺序考虑：

1. 新增歪头、转头和更多点击反馈；
2. 小程序／App 端角色查看与互动；
3. 投喂、心情和简单养成；
4. 狗和其他宠物模板；
5. 多色板和采购清单；
6. AR 平面放置；
7. 多方向角色、行走与转身。

任何后续阶段都继续复用本规格中的版本化拼豆角色资产，而不是重新定义另一套角色格式。
