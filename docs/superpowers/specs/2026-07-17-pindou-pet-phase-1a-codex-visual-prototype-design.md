# 拼豆虚拟宠物 Phase 1A：Codex 合成三视图视觉原型设计规格

状态：已批准并冻结为 Phase 1A 实施基线

日期：2026-07-17

阶段定位：Phase 0 之后、真实 Provider 可行性硬门禁之前的人工在环视觉验证

## 1. 决策背景

Phase 0 已经建立 Web/API 骨架、存储、队列和 Provider 合同。原 Phase 1 计划要求接入真实生成服务并完成三只真实猫的硬门禁。当前决定先不申请或购买生成 API，不把 Codex 会话包装成产品后端，而是在开发阶段用 Codex 图像生成能力和子 agent 验证视觉方向。

Phase 1A 只回答一个问题：

> 三张属于同一只猫的多视角参考图，能否生成一张一眼可认、具有明确拼豆质感的静态 2.5D 宠物角色？

本阶段使用合成猫参考图，因此通过只能证明视觉流程值得继续，不能证明真实宠物还原、网页自动生成、稳定延迟、任务恢复、批量服务或生产成本已经可行。

## 2. 与既有阶段的关系

- 本规格不修改 Phase 0 已冻结的工程基础。
- 本规格在原 `phase-1-provider-feasibility` 之前插入 Phase 1A。
- 原真实 Provider、真实照片和三猫硬门禁保留为后续 Phase 1B，不因 Phase 1A 通过而自动视为通过。
- Codex 和子 agent 是开发期人工编排工具，不是 Web 应用运行时依赖；网页用户不能直接调用当前任务或其子 agent。
- 本阶段不使用用户提供的 API Key，但图像仍由外部模型能力生成，不等于本地离线推理，也不承诺免费额度或服务等级。

## 3. 目标和成功定义

Phase 1A 必须完成以下闭环：

1. 冻结一只特征明显的短毛三花猫身份卡。
2. 生成同一只猫的正面、猫左前 45°、猫右前 45°摄影风格参考图。
3. 通过独立一致性检查后，将三视图作为同一组输入。
4. 最多生成三个静态 2.5D 拼豆角色候选。
5. 用户选中一个候选，并且最多进行一轮文字校正。
6. 交付高清透明角色、58×58 视觉预览和 464×464 最近邻放大预览。
7. 用户明确给出 `VISUAL_PROTOTYPE_PASS` 或 `STOP_REVISE_STYLE` 决策。

优先级固定为：同一只猫的身份辨识度第一，拼豆艺术效果第二。不得用更强的风格化掩盖脸型、毛色或标志花纹错误。

## 4. 范围

### 4.1 包含

- 一只合成短毛三花猫。
- 三张合成摄影风格参考图。
- 一个固定静态角色姿势。
- 最多三个拼豆角色候选。
- 最多一轮文字校正。
- 高清透明 PNG、58×58 预览和 464×464 最近邻预览。
- 本地身份卡、提示词、生成尝试、人工判断和文件哈希记录。

### 4.2 不包含

- 真实宠物照片和真实宠物辨识度结论。
- 付费 Provider 调查、API Key、Provider adapter、幂等恢复和服务等级验证。
- 上传页、项目流程、任务队列和用户自助生成。
- 自动抠图模型、六部件拆层、关节点、动作绑定和互动。
- 真实拼豆色板、逐豆编辑、四块 29×29 底板和 PNG/PDF 实体图纸导出。
- 120 秒产品性能门禁；本阶段可记录人工工作流时间，但不得将其解释为产品延迟。
- 三维网格、骨骼蒙皮和任意角度旋转。

## 5. 合成猫身份卡

首个测试对象固定为一只容易跨视角辨认的短毛三花猫：

- 白色为身体主色；
- 绿色眼睛；
- 猫左眼周围有稳定橘色斑块；
- 猫右耳及相邻头顶有稳定黑色斑块；
- 背部具有可辨认但不过度碎片化的橘黑斑块；
- 尾巴为橘黑环纹，末端深色；
- 中等体型、短毛、自然比例；
- 不佩戴项圈、衣服或饰品。

“猫左／猫右”始终指猫自身的解剖方向，不随画面视角改变。提示词、身份卡、审查记录和文件名使用 `FRONT`、`CAT_LEFT_FRONT_45`、`CAT_RIGHT_FRONT_45`，避免把画面左／右与猫左／右混用。

## 6. 三视图参考图设计

### 6.1 采用方案

不让三个 agent 相互独立地各生成一张猫图。先冻结身份卡，再一次生成一张包含三个视角的统一母版，最后按固定面板顺序裁成三张独立 PNG。这样可以降低脸型、体型和花纹在不同调用之间漂移的概率。

母版从左到右固定为：

1. `FRONT`：正面全身；
2. `CAT_LEFT_FRONT_45`：相机位于猫左前方约 45°；
3. `CAT_RIGHT_FRONT_45`：相机位于猫右前方约 45°。

三个面板使用同一浅灰摄影棚背景、柔和中性光、相近相机高度和自然站姿。必须完整显示耳朵、四肢和尾巴；不添加文字、水印、道具、滤镜或拼豆效果。面板之间保留清晰空白分隔，裁切后每张参考图的有效区域至少为 512×512。

### 6.2 子 agent 分工

- **身份 agent**：把冻结描述转换为结构化身份卡和生成约束，不生成图片。
- **三视图生成 agent**：只根据身份卡生成统一母版，不自行改变品种、花纹或姿态要求。
- **一致性审查 agent**：在不知道后续拼豆候选的情况下，对脸型、眼色、猫左／猫右斑纹、背部斑纹、体型和尾纹逐项检查。
- **根 agent**：保存资产、裁切面板、计算哈希、核对方向和决定接受或整张重生成。

子 agent 的意见是辅助证据，根 agent 不得只凭 agent 的“通过”描述接受图片，必须实际检查生成文件。

### 6.3 失败处理

出现以下任一情况时整张母版作废，不单独修补某一面板：

- 三个视角看起来不是同一只猫；
- 猫左／猫右标志斑纹镜像或交换；
- 眼睛、耳朵、体型或尾纹明显漂移；
- 任一视角缺失身体、四肢或尾巴；
- 出现多余肢体、项圈、文字、水印或拼豆化；
- 面板边界无法可靠裁切。

最多允许两张母版被拒绝。第三张仍不合格时停止生成，请用户决定是简化身份卡、改变花纹还是结束本轮，避免无限消耗生成额度。

## 7. 拼豆角色候选设计

### 7.1 固定角色姿势

三个候选使用同一姿势：脸朝向用户，身体向画面右侧偏转约 20°，尾巴位于画面右侧，完整角色居中，不裁切耳朵、爪或尾巴。姿态是静态 2.5D 插画，不表达完整三维结构。

### 7.2 视觉要求

- 角色保留身份卡中的脸型、绿色眼睛、猫左眼橘斑、猫右耳黑斑、身体主色和尾巴环纹。
- 由清晰可见、大小基本一致的拼豆颗粒构成，具有轻微塑料立体感和统一光照。
- 轮廓和主要花纹优先使用大块、连贯的豆格，不使用毛发噪点或高频抖动。
- 输出为真正带 alpha 通道的透明 PNG；棋盘格或纯色背景的视觉模拟不算透明。
- 不出现底板、网格文字、品牌标识、阴影背景、道具、多余肢体或分离漂浮的豆粒。
- 三个候选可以在颗粒密度、轮廓圆润度和轻微立体感上有小幅差异，但不得改变身份或姿势。

### 7.3 候选和校正规则

首轮最多生成三个候选。用户选择其中一个，或者判定三者全部不合格。用户选中后只允许一轮自然语言校正，校正必须明确指向身份、颜色、花纹、姿态或拼豆质感中的具体问题。

校正不能把角色换成另一只猫，不能增加新配饰，也不能顺带进入拆层、动作或实体图纸范围。一轮校正后仍不合格，结果记为 `STOP_REVISE_STYLE`，回到书面风格定义而不是继续无限重试。

## 8. 58×58 视觉预览

从最终高清候选生成：

- `preview-58.png`：将完整角色等比放入 58×58 透明画布；
- `preview-464.png`：把 58×58 图以 8 倍最近邻放大到 464×464，用于人工评审。

缩放过程固定使用最近邻，不做平滑、锐化、重新绘制或新一轮生成。预览只用于判断低分辨率轮廓和主要花纹是否仍可辨认，明确标记为 `NOT_A_PHYSICAL_BEAD_EXPORT`。它不应用真实拼豆色板、不统计豆数，也不代表已经完成 58×58 分层角色资产。

## 9. 数据流与本地资产

所有生成媒体和运行记录写入被 Git 忽略的：

```text
var/phase-1a/synthetic-cat-01/
  identity/
    identity-card.json
  prompts/
    reference-master.md
    character-candidates.md
    correction.md
  references/
    three-view-master.png
    front.png
    cat-left-front-45.png
    cat-right-front-45.png
  reviews/
    reference-consistency.json
  candidates/
    candidate-01.png
    candidate-02.png
    candidate-03.png
  selected/
    character-hd.png
    preview-58.png
    preview-464.png
  manifest.json
```

未发生文字校正时不创建 `correction.md`，不存在的候选文件也不得用空文件占位。`manifest.json` 记录身份卡哈希、母版尝试次数、面板顺序和哈希、提示词文件哈希、生成顺序、用户选择、最终文件哈希和阶段决策。它不记录账户凭证、会话令牌或绝对路径。

生成图片、提示词实参和运行 manifest 不提交 Git。后续实施可以提交可复用的无秘密脚本、测试和脱敏模板，但必须由单独实施计划明确列出。

## 10. 验收标准

### 10.1 参考图门

- 三张图具有相同脸型、眼睛、耳形、体型和尾巴形态；
- 猫左眼橘斑、猫右耳黑斑及尾巴环纹在三个视角保持同一解剖位置；
- 三张图均为完整全身摄影风格，没有拼豆化、配饰、文字和异常肢体；
- 方向与 `FRONT`、`CAT_LEFT_FRONT_45`、`CAT_RIGHT_FRONT_45` 定义一致。

### 10.2 角色门

- 用户能够一眼判断角色与三张合成参考图属于同一只猫；
- 脸型、绿色眼睛、主要脸部斑纹、身体主色和尾巴环纹得到保留；
- 脸正对用户，身体向画面右侧约 20°，尾巴位于画面右侧；
- PNG 具有真实透明通道，没有多余肢体、错误花纹或背景；
- 高清图能明显辨认拼豆颗粒，颗粒不破坏关键身份特征；
- 58×58／464×464 预览仍能辨认轮廓和主要花纹；
- 用户在最多一轮文字校正后明确批准最终候选。

全部条件满足时记录 `VISUAL_PROTOTYPE_PASS`。任一条件不满足，或用户认为不像同一只猫，则记录 `STOP_REVISE_STYLE`，不得以子 agent 自评、生成次数或“整体看起来不错”替代用户批准。

## 11. 验证与测试边界

实施计划至少覆盖：

- 身份卡字段和猫左／猫右术语检查；
- 三面板顺序、裁切范围和最小有效尺寸检查；
- PNG 解码、尺寸、alpha 通道和内容哈希检查；
- 58×58 最近邻缩放及 464×464 放大尺寸检查；
- manifest 不包含绝对路径、密钥、令牌和 Base64 图片检查；
- `var/` 资产不会出现在 Git staged/tracked 文件中的检查；
- 人工参考图门和角色门记录完整性检查。

自动测试只能证明文件和记录符合合同，不能自动证明角色“像同一只猫”。最终身份与风格判断必须由用户完成。

## 12. 阶段出口

Phase 1A 只有两个合法出口：

1. `VISUAL_PROTOTYPE_PASS`：视觉路线值得继续。下一步重新确认是用真实照片在 Codex 中做第二轮人工验证，还是进入真实 Provider／自托管模型设计；不自动开始网页产品化。
2. `STOP_REVISE_STYLE`：停止拆层、动画和网页功能，先修改身份卡、姿势或拼豆视觉定义，再开启新的受限验证轮次。

无论哪个出口，本阶段都不得宣称“真实宠物生成已验证”“网页可以自动生成”或“Phase 1 Provider 硬门禁已通过”。
