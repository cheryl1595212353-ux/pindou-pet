# 拼豆宠物三视图个性轮廓体素建模设计

日期：2026-07-19  
状态：已批准方向的实施规格

## 1. 目标

把当前“所有猫共用固定几何、只改变颜色”的演示改为真正由正面、侧面、俯视三张图片驱动的个性化体素模型。五只内置猫必须具有不同的头部宽度、身体长宽、腿部比例、耳朵高度和尾巴尺寸，同时继续支持旋转、缩放、三种相机预设、呼吸、眨眼、摇尾和点击跳跃。

本轮仍只使用已有五只测试猫的 15 张内置图片，不增加上传入口、付费 API、云端推理或通用自然背景分割。代码边界需允许后续把上传照片送入同一轮廓与视觉外壳管线。

## 2. 方案选择

采用“三视图视觉外壳（visual hull）＋独立尾巴估计＋人工校正”。

- 不采用单一参数模板变形，因为它只能近似猫的类别，不能让局部轮廓真正服从图片。
- 不采用 NeRF、Gaussian Splatting 或生成式多视图网格重建，因为当前 Web MVP 不应依赖 GPU、模型下载或付费服务。
- 三视图视觉外壳对干净、方向一致的工作室图片具有确定性，可在浏览器本地运行，并天然输出适合像素风的体素占用网格。

## 3. 输入契约

每只猫固定提供：

- `front.png`：正面，提供宽度－高度轮廓及正面颜色；
- `side.png`：猫头朝左的侧面，提供长度－高度轮廓及侧面颜色；
- `top.png`：俯视图，提供长度－宽度轮廓及顶部颜色。现有素材的头部方向不完全一致：`cat-01`、`cat-02` 头朝图像上方，`cat-03`、`cat-04`、`cat-05` 头朝图像下方；资源配置必须显式记录方向，规范化时统一为头部位于负 `x` 方向。

首版输入假设：背景接近白色、整只猫完整可见、没有其他前景物体、三张图属于同一只猫且方向符合上述约定。任一图片加载或解析失败时，页面显示非阻塞提示并回退到原固定体素模型。

## 4. 轮廓提取与对齐

浏览器使用离屏 `canvas` 读取三张图片，并执行确定性的本地处理：

1. 把最长边缩小到受控尺寸，限制处理成本；
2. 从图片边缘估计背景颜色；
3. 使用强／弱前景双阈值提取主体，保留与强前景相连的弱前景像素；
4. 执行一次小半径闭运算、孔洞填充和最大主体保留，去除背景噪声；
5. 根据主体包围盒裁切，并将脚底、身体中心和头部方向对齐；
6. 重采样为规范化轮廓网格：正面 `24×48`、侧面 `56×48`、俯视 `24×56`。

侧面和俯视图中的细长尾巴会使三视图姿态不一致，因此身体视觉外壳不直接把尾巴纳入求交。处理器根据轮廓列宽／行宽找到连续的躯干核心区，尾巴长度与粗细则从俯视图后方细长区域估计，必要时使用外观配置中的安全回退值。

所有轮廓处理函数保持纯函数，可使用合成 RGBA 数据进行单元测试。真实图片加载单独封装，不与体素几何算法耦合。

## 5. 视觉外壳生成

详细模式使用 `56×48×24` 的长度－高度－宽度体素网格；性能模式使用 `36×32×16` 网格。对候选体素分别投影到正面、侧面和俯视轮廓，三个投影均位于前景时才保留该体素。

为容忍生成图片中轻微的姿态差异，每个规范化轮廓先膨胀一个网格单元再求交。求交后：

- 移除微小孤立连通分量；
- 仅保留具有至少一个空邻居的表面体素；
- 保持脚底位于 `y=0`；
- 使头部位于负 `x` 方向、尾部位于正 `x` 方向；
- 记录模型边界、脸部平面、眼睛／鼻子锚点、身体中心和尾巴连接点。

尾巴使用从俯视轮廓估计出的长度与粗细生成三段圆角体素棱柱，继续复用现有三级尾巴动画骨架。不同猫的尾巴长度和粗细必须可辨识。

## 6. 照片颜色投射与像素风

每个表面体素根据其主要朝向选择颜色来源：

- 朝前的表面优先采样正面图；
- 左右侧表面优先采样侧面图；
- 顶部表面优先采样俯视图；
- 背面、底部或采样缺失时使用最近的有效前景颜色或猫咪基础色。

三张图的有效前景像素共同生成不超过 16 色的确定性调色板，采样颜色映射到最近的调色板颜色，避免把摄影噪声直接变成杂乱色块。人工补出的轮廓使用最近前景色，找不到时使用外观基础色。

眼睛和鼻子仍作为小型独立体素细节渲染，其位置由视觉外壳边界按比例计算，不再使用固定世界坐标。

## 7. 人工校正

左侧控制区增加可折叠的“轮廓校正”面板，包含：

- 正面／侧面／俯视轮廓切换；
- `补轮廓` 与 `擦轮廓` 两种画笔；
- 轮廓预览画布；
- 头宽、身体长度、腿长、耳朵高度、尾巴粗细五个滑杆；
- `恢复自动轮廓` 按钮。

轮廓画笔直接修改规范化二维蒙版，再重新生成视觉外壳；它不是在 3D 画布中逐块编辑。滑杆只对生成结果做有界形变，范围为默认值的 `80%–120%`，避免破坏动画锚点。每只内置猫在当前页面会话中保存自己的校正状态，切猫再切回时不丢失，刷新页面后恢复自动结果。

减少动态效果模式下，轮廓编辑仍可用，但不播放额外过渡动画。

## 8. 组件与数据流

新增边界：

- `threeViewRaster.ts`：图片加载、RGBA 前景提取、裁切和规范化；
- `visualHull.ts`：三视图求交、连通分量、表面剔除、尾巴和锚点生成；
- `photoPalette.ts`：调色板提取、视角颜色采样和量化；
- `useThreeViewCatModel.ts`：图片缓存、异步状态和精细／性能模型生成；
- `PersonalizedVoxelBody.tsx`：实例化渲染个性化主体、尾巴、眼睛和鼻子；
- `ShapeCorrectionPanel.tsx`：蒙版画笔、滑杆和恢复操作。

数据流：

`三张内置图片 → RGBA → 三张规范化蒙版／颜色图 → 人工蒙版覆盖 → 视觉外壳 → 有界体型形变 → 表面颜色量化 → InstancedMesh`。

现有固定模型保留为加载中和错误回退，不再作为正常情况下五只猫的共享轮廓。

## 9. 性能与缓存

- 同一只猫的三张图片只解析一次，结果在模块级 Promise 缓存中复用；
- 切换视角或播放动画不得重新解析图片；
- 只有切猫、修改轮廓或滑杆时重新计算模型；
- 视觉外壳生成不得创建每体素一个 React 元素，主体和每段尾巴继续使用 `InstancedMesh`；
- 详细模式桌面浏览器目标仍为至少 45 FPS；
- 轮廓或滑杆操作后，模型更新时间目标为 200ms 内；
- 性能模式仍使用个性轮廓，仅降低网格分辨率。

## 10. 错误处理

- 图片加载中：显示“正在从三视图生成轮廓”，并暂时渲染原固定模型；
- 单张图加载失败或 `canvas` 读取失败：显示“个性轮廓生成失败，已使用安全模型”；
- 提取到的主体过小、视觉外壳为空或体素数量越界：拒绝该结果并回退；
- 人工擦除导致空模型：保留上一个有效模型并提示恢复自动轮廓；
- 回退不能影响猫咪选择、相机、精细度或互动状态。

## 11. 测试策略

### 纯函数测试

- 白背景合成 RGBA 图可提取预期主体，边缘噪声被移除；
- 蒙版裁切、缩放、膨胀、画笔增删和恢复结果确定；
- 三个已知轮廓生成预期视觉外壳，内部体素被剔除；
- 修改任一视图轮廓会改变生成的 3D 边界；
- 五组真实内置图片的生成结果非空，且至少四项轮廓指标存在差异；
- 颜色量化不超过 16 色且同一输入结果一致；
- 性能模式体素数低于详细模式，但边界比例接近；
- 五个滑杆只影响其目标区域并保持有限范围。

### React 测试

- 加载完成后渲染个性模型，加载失败时回退并提示；
- 切换五只猫会使用不同模型；
- 精细／性能模式都使用个性轮廓；
- 轮廓画笔、滑杆、恢复按钮和按猫保存状态可用；
- 当前相机和猫咪状态在校正时不丢失；
- 原有点击、动画、低帧率和 WebGL 回退测试不回归。

### 浏览器验收

- 五只猫正面、侧面和俯视轮廓肉眼可区分；
- 橘猫更短小、银灰英短更敦实、布偶猫更宽厚且尾巴更粗长；
- 至少对一只猫实际补一次和擦一次轮廓，3D 外壳随之变化；
- 五个滑杆均产生对应而非全局无差别缩放；
- 模式切换、三种相机、自由旋转、缩放、点击、呼吸、眨眼和摇尾正常；
- 1440×900 与 390×844 均无主要控件遮挡；
- 控制台无错误，详细模式连续 10 秒平均至少 45 FPS。

## 12. 验收标准

本轮仅在以下条件全部满足时完成：

1. 正常路径不再把同一组体素坐标用于五只猫。
2. 三张图片实际参与轮廓生成，而不是只用于缩略图或颜色参考。
3. 五只猫至少在头宽、长高比、体宽或尾巴尺寸中存在可测量差异。
4. 精细和性能模式均保持每只猫自己的轮廓。
5. 用户可以在三视图蒙版上补／擦轮廓，并通过五个滑杆校正体型。
6. 照片颜色经过不超过 16 色量化后投射到表面。
7. 当前动画和互动无回归，错误时安全回退。
8. 单元测试、React 测试、类型检查、生产构建和项目统一检查全部通过。
9. 浏览器视觉、交互、窄屏和性能验收通过，控制台错误为零。

## 13. 后续范围

真实照片上传、自然背景分割、关键点模型、任意拍摄方向自动校正、服务端缓存、账号保存和 AR 放置留到后续独立规格。本轮不会把干净内置素材的成功描述成通用照片重建已经完成。
